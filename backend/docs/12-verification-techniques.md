# 12. Методы верификации — E2E, property, differential

Основано на инженерных практиках Claude Code: https://claude.dev/blog/how-the-claude-code-team-thinks-about-verification/ . **Не трактуйте шаблоны как уже выполненные проверки.**

## E2E — пользовательский сценарий

Для изменения UX/бизнес-логики подтвердите путь от входного действия до фактического результата через браузер, simulator, API harness или запущенный сервис.

- Описывайте стартовые данные, права пользователя, шаги и точный ожидаемый результат.
- Сохраняйте trace, минимальные безопасные screenshots, логи с корреляцией; фиксируйте версию кода и окружение.
- Проверяйте негативные и альтернативные пути (guest, expired session, 403/429/500, offline, retry, back/refresh).
- Для backend используйте реальную БД в **изолированном тестовом окружении**, если важны транзакции, гонки и миграции.

## Property-based — инварианты

Сформулируйте свойство, затем создайте репрезентативные генераторы и shrinking. Примеры:

- `decode(encode(x)) == x` для поддерживаемого домена;
- повторный idempotent retry не создаёт вторую запись;
- баланс или счётчик не переходит запрещённые границы;
- доступ к чужим данным всегда denied;
- round-trip/timezone/serialization не теряют значимые поля.

Возможные инструменты: fast-check (TS), Hypothesis (Python), proptest (Rust); в Go — fuzzing через `go test -fuzz` и табличные тесты. Seed, shrinking counterexample и окружение сохраняйте.

## Differential — старая/новая система

Для миграции/рефакторинга подавайте одинаковые входы в baseline и candidate. Сравнивайте значимое поведение (выход, side effects, DB rows, HTTP контракт, state transitions), нормализуя только **явно несущественные** различия. Список допустимых изменений должен быть утверждён заранее.

## Правильный порядок

Проверьте сначала дешёвые детерминированные проверки, затем интеграцию, затем E2E и security/performance по риску. Флейки тест — отдельный дефект проверки; не лечите его бесконечным retry.
