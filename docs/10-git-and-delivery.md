# 10. Git и поставка

## Коммиты

Стандарт исходного проекта — Conventional Commits, subject на русском:

```text
feat(auth): добавить восстановление сессии
fix(feed): устранить дублирование элементов
refactor(shared): выделить типы
```

`type(scope)!: ...` и footer `BREAKING CHANGE:` — при нарушении обратной совместимости.
Коммит предметный, с минимальным diff; сообщение отражает **фактически** сделанное.

## Dirty worktree / независимые изменения

- Сначала `git status`/`git diff`. Не откатывайте чужие незакоммиченные правки.
- При значимом риске используйте отдельную ветку/worktree; не пересоздавайте и не удаляйте чужие worktrees.
- Перед коммитом проверяйте staged diff и секреты. Перед push — target remote, SHA, защиту ветки и разрешение.
- Не изменяйте тесты, gates и baseline вместе с реализацией ради сокрытия регрессий. Изменения verifier требуют отдельного ревью.

## Поставка

- Push, release tag, merge, запуск CI с побочными эффектами и deployment требуют явно установленного разрешения.
- Технический тег, публикация пользовательского changelog и production deployment — разные действия.
- Утверждения «прошёл CI» подтверждаются реальным run ID / commit SHA и состояниями required jobs.
- Оставшиеся `SKIP`/`SETUP_FAILURE` не называйте зелёным релизом. Required gates fail-closed.
- Внедрение новых gates: `off` → `observe` → `enforce` после проверки ложных срабатываний; **без автоматических обходов критических gates**.

Привязка конкретного Git-тега к деплою и инструкции релиза должны храниться в профиле целевого проекта. Схема Soobota `v*.*.*` и генерация `/whats-new` не являются универсальным правилом.
