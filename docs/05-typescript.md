# 05. TypeScript

Типы должны описывать контракты и runtime-валидацию, а не скрывать неопределённость.

- Избегайте `any`. Для неизвестных входов применяйте `unknown`, type guard / schema validation.
- Не используйте `as Type` для обхода ошибки компилятора. Обоснованные `as const`, узкие утверждения после проверки данных и типовые ограничения внешних библиотек допустимы с понятным основанием.
- Для boolean используйте семантику `is` (состояние), `has` (наличие), `should` (поведение), `can` (право), если нет устойчивого публичного API с другими именами.
- Соглашение исходного проекта — `type` по умолчанию; `interface` допустим для открытых расширяемых контрактов и совместимости с библиотеками.
- Для хуков полезны `UseSomethingProps`, `UseSomethingResult` и, когда требуется, `UseSomethingHook`.
- Используйте Utility Types (`Pick`, `Omit`, `Partial`, `Required`, `Record`, `ReturnType`), если они уменьшают дублирование.
- Generic-параметры называйте семантически (`TData`, `TItem`) при наличии нескольких значений; одиночный `T` допустим в узком очевидном контексте.
- После изменения типов запустите существующую команду проекта (`typecheck`, `tsc --noEmit` и т. п.), предварительно убедившись в package scripts и конфиге.

При изменении внешнего API проверяйте как успешные, так и ошибочные payload'ы. TypeScript-проверка не заменяет runtime validation.
