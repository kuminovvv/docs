# AGENTS.md — Frontend

> **Область:** шаблон инструкций для frontend-кода. В этом репозитории он расположен в `docs/frontend/` как источник правил. В рабочем приложении разместите адаптированную копию в каталоге frontend-кода, чтобы агент мог обнаружить её по расположению файла. Здесь нет общего корневого `AGENTS.md`.

## Project overview — назначение и область

- Перед задачей установите цель приложения, затронутые маршруты, UI-состояния, контракты API и критерии приёмки из реального проекта.
- Выполняйте запрос пользователя, не выдумывайте бизнес-требования. Если документация, код, тесты и фактическое поведение расходятся, сообщите о конфликте.
- Для небольших изменений изучайте только относящиеся к ним файлы и зависимости; для нетривиальных — кратко зафиксируйте scope, план и риски.

## Tech stack — стек и версии

- Подтвердите фреймворк, архитектуру и версии по `package.json`, lockfile, конфигам и профильному документу проекта. **Не считайте React, Next.js или FSD обязательными по умолчанию.**
- При использовании версиозависимого API проверьте официальную документацию, changelog, статус deprecated и migration guide **для установленной версии**. Не копируйте устаревшие `experimental`-флаги и не повышайте версию зависимостей без необходимости.
- Различайте Next.js App Router/Pages Router и React Server/Client Components по фактическому коду.

## Development — установка, запуск и сборка

- Возьмите менеджер пакетов и реальные команды install/dev/build/typecheck/lint из scripts, lockfile и CI **целевого приложения**.
- Если команда или переменная окружения не указана, выясните её из проекта; не объявляйте выдуманный `npm test` обязательным.
- Используйте тестовые учётные записи и изолированные среды. Не обращайтесь к production и приватным данным без разрешения.

## Code conventions — архитектура и стиль

- Следуйте принятым соглашениям проекта и поддерживайте минимальный объяснимый diff. Не создавайте новых слоёв, wrappers, hooks или абстракций только ради стиля.
- Для Next.js соблюдайте Server/Client-границы, сериализацию, изоляцию персонализированного кеша и серверную авторизацию мутаций.
- Не заменяйте семантический HTML, доступность, keyboard/focus и обработку ошибок декоративными обходами.
- Применяйте дополнительные правила **только по активному стеку**: [React](react-components.md), [TypeScript](typescript.md), [Next.js](nextjs.md), [FSD](fsd.md), [performance](performance.md), [error handling](error-handling.md), [UI/a11y](ui-context-risks.md).

## Testing — проверка и доказательства

- Для изменённого поведения выполняйте доступные lint, typecheck, unit и build; для интерактивного UI — релевантный браузерный/E2E-сценарий. Выбирайте проверки по риску, а не запускайте всё без причины.
- Проверяйте happy path и необходимые негативные сценарии: guest/auth, 401/403, loading/error, keyboard, мобильный viewport, SSR/hydration, caching и refresh. При изменении API проверьте runtime-валидацию данных.
- Записывайте точную команду/сценарий, окружение, проверенный SHA, результат и безопасные артефакты. **PASS** — только реально выполненная проверка с доказательством; `SKIP`, `BLOCKED`, `FLAKY`, timeout и `SETUP_FAILURE` — не PASS.
- Не ослабляйте тесты, CI-gates и проверяющие инструменты ради зелёного статуса. Для изменений verifier требуется отдельное ревью относительно baseline.

## Security — безопасность и приватность

- Не выводите секреты, токены, cookie, ПДн или приватные payload в код, логи, отчёты и сторонние сервисы.
- Права проверяются на сервере: скрытый UI и TypeScript-типы не заменяют авторизацию, валидацию или защиту от утечки между пользователями.
- Новые SDK, аналитика, CDN и внешние интеграции требуют оценки передаваемых данных и разрешения в рамках проекта.

## Delivery — коммиты, PR и завершение

- Перед изменением и коммитом проверьте Git status/diff; не перезаписывайте чужие незакоммиченные изменения.
- Push, merge, запуск CI с побочными эффектами, release и deployment — только при явном разрешении. Отчёт всегда содержит изменённые файлы, команды/результаты, ограничения проверки и остаточные риски.
- Для рискованного diff ориентируйтесь на [review/gates](../13-review-and-gates.md), [verification](../09-testing-and-verification.md), [security](../14-security-and-privacy.md) и [git/delivery](../10-git-and-delivery.md).
