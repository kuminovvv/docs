# 15. Адаптация правил к проекту

Не подключайте все инструкции ко всем репозиториям без определения активного стека и scope.

1. Создайте `docs/project-profile.md` из [шаблона](templates/project-profile.md) **в целевом репозитории**.
2. Укажите стек и фактические версии, применимые каталоги `docs/frontend/` и/или `docs/backend/`, пакетный менеджер, команды запуска/линтинга/тестов, покрытие, тестовую БД, CI, владельца релизов, ограничения безопасности, запрещённые пути.
3. Определите, какие проверки обязательны при каких триггерах diff; закрепите критические gates в CI с защищёнными правилами.
4. Проект может уточнить соглашения об именах/структуре, но не должен молча ослаблять правила по безопасности, секретам, фальсификации PASS и внешним действиям.
5. Если старые проектные инструкции расходятся с текущими правами пользователя или архитектурой — зафиксируйте решение в ADR/PR; не выбирайте произвольно.

**Примеры специфики, которую НЕ следует переносить в общий набор:** адреса серверов/доступы, боевые флаги, теги деплоя, команды конкретного GitLab CI, юридические реестры провайдеров, сроки задач, журналы доказательств старых коммитов.
