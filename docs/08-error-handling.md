# 08. Ошибки и наблюдаемость

Ошибки должны быть явными, классифицируемыми и полезными для пользователя и диагностики.

- Для `fetch` проверяйте `response.ok`, контракт error body и таймауты/abort; не проглатывайте причину.
- Различайте transport failure, HTTP/API error, validation error, authorization error и unsupported state.
- Используйте существующий UI feedback (toast, inline, error boundary), избегая дублей.
- Не логируйте пароли, access/refresh токены, секреты, cookie, ПДн, приватные payload'ы и полный URL с чувствительными query-параметрами.
- Логи для backend — структурированные, с безопасным Request-ID/trace-id и без приватных identifiers, если можно их исключить.
- Комментарии описывают причину и ограничения, а не очевидную реализацию.

Ложноположительный UI-success при серверном fail считается дефектом даже при отсутствии исключения в клиенте.
